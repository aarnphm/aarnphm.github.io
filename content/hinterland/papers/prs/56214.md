**andyluo7** (2026-09-11T01:53:12Z):

Hi @zyongye — while validating #56214 on 8x MI300X/gfx942, we found one gfx942-specific correctness issue.

On gfx942, `EmulationMxfp8LinearKernel.process_weights_after_loading()` can replace the original one-byte MXFP8 `wo_a.weight` with BF16 while retaining `weight_scale` or `weight_scale_inv` as metadata. `_get_cached_wo_a_bf16()` then interprets the retained scale as evidence that the weight is still FP8 and applies it again, causing double dequantization before the TP all-reduce.

The fix is to apply block scaling only while the weight still uses one-byte storage:

```python
if wo_a_scale_param is not None and wo_a.weight.element_size() == 1:
```

I also added regression coverage for already-dequantized BF16 weights retaining either scale attribute.

Validation on 8x MI300X/gfx942, TP8:

- Focused ROCm tests: `4 passed, 61 deselected`
- Direct retained-scale probes: exact BF16 match for both `weight_scale` and `weight_scale_inv`; the unfixed path produced an output/expected norm ratio of `0.25`
- Full official GSM8K evaluator: `1197/1319 = 90.7506%`
- GSM8K contract: 8-shot, 1,319 questions, max tokens 256, temperature 0, seed 42, no explicit concurrency override
- Zero invalid responses, zero API errors, and zero fatal server-log patterns
- Full model-default 1,048,576-token context, `FULL_AND_PIECEWISE` graphs, DSpark-5, and `AITER_TRITON_MXFP4_BF16`

The evaluator is byte-identical to the one used by #56342, and the MI300X result is within that PR's published fused MI355X range of 89.76%-91.36%.

I have this prepared as a signed one-commit patch. Since #56214 currently needs a rebase against `main`, would you prefer to cherry-pick it, or should I push it directly to `dsv41-feat` after the rebase?
