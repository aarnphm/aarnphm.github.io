# #58180 [Agents] Add model-optimization skill with performance goal matrix

https://github.com/vllm-project/vllm/pull/58180 · faradawn · CLOSED · created 2026-09-22T16:11:52Z · merged <no value>

## Overview

"Optimize this model" is not an actionable instruction for a coding agent, and
it is roughly what agents are given today. It does not say which parallelism to
tune, which serving regime and request shape to tune for, which harness defines
the number, or whether the target is throughput or perf/W. Agents therefore pick
a cell implicitly, optimize it, and report a win that does not hold in the
configuration the maintainer cares about.

This adds a `model-optimization` skill under `.agents/skills/` that forces those
five choices to be made and stated before any code changes, anchored on a
performance goal matrix of parallelism x regime x shape. It also bundles a
mergify rule so the existing `agents` label is actually applied to agent
instruction and skill changes.

Related: #57084 (`pr-checklist` skill, whose template and checklist this
description follows).

## Claims

- A skill that converts a vague optimization request into a single named goal:
  parallelism (TP, TP+EP, DP+EP, DCP, PCP+EP), regime (decode / prefill /
  mixed), shape (concurrency and KV or prompt length), harness, and metric.
- The matrix makes explicit that the columns pull in opposite directions —
  1 request at 50K KV is latency- and bandwidth-bound while 128 requests at
  50-70K KV is throughput-bound and KV-capacity-limited — so a "decode speedup"
  claim is not reviewable without naming the column.
- Guidance that `vllm bench serve` numbers and external leaderboard numbers
  (SemiAnalysis InferenceX, Artificial Analysis) are not interchangeable,
  because the request mix and SLA definitions differ, with a worked mapping from
  a matrix cell to `vllm bench serve` flags.
- Guidance that perf/W ranks configurations differently from raw throughput, so
  the metric must be fixed up front rather than chosen after the measurement.
- A mergify rule applying the `agents` label to changes under `AGENTS.md`,
  `.agents/`, `.claude/`, and `docs/contributing/editing-agent-instructions.md`.

This PR claims better-specified optimization work. It does not claim any
measured performance improvement; no kernel, model, or serving code is touched.

## Details

**Why a skill rather than `AGENTS.md`.** This is area-specific knowledge, which
`docs/contributing/editing-agent-instructions.md` routes to a domain guide, and
`AGENTS.md` loads on every request. The repo already has a `.agents/skills/`
directory, so this adds no new mechanism.

**Why the shapes are the ones listed.** They are the cells where the answer
actually diverges: single-request long-context decode (bandwidth-bound),
high-concurrency long-context decode (KV-capacity-bound), one large prefill
(compute-bound), and several small prefills (batching and launch overhead).
Reviewers may want to argue about the specific lengths; the cells are more
important than the exact numbers, and the skill is cheap to amend.

**The matrix is deliberately empty.** It is a checklist of goals to name, not a
results table. Cells are left blank rather than pre-filled with targets or
applicability marks, since which combinations are worth pursuing is a moving
target and hardcoding it would go stale.

**Tradeoff.** The skill adds process to performance work that previously had
none. The cost is a few lines in a PR description; the benefit is that a
performance claim becomes falsifiable. It does not gate anything in CI.

**Limitation.** A skill only helps agents that read it. Nothing enforces that
the five choices are stated, and this PR deliberately does not add such
enforcement to `AGENTS.md` or the PR template.

**The mergify rule is bundled rather than separate** because a one-rule change
would be exactly the low-value single-edit PR `AGENTS.md` asks contributors not
to open, and because `docs/contributing/labels.md` asks that label rules land
with the change that motivates them.
