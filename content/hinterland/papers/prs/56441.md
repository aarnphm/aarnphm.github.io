# #56441 [Perf][DSpark] Add KV-only context insertion across V4.1 cache formats

https://github.com/vllm-project/vllm/pull/56441 · 0z5a · MERGED · created 2026-09-11T09:42:40Z · merged 2026-09-16T04:34:56Z

Replace the DeepSeek-V4.1 DSpark context insertion call's unused query allocation and query work with a KV-only wrapper. Dispatch the existing CUDA KV math with zero query heads for packed uint8 `fp8_ds_mla`, BF16 and ordinary FP8 e4m3fn caches. Keep projection, `kv_norm`, scheduling and acceptance logic unchanged. Validate device/dtype/layout inputs and preserve padded page strides.

**Rebase validation (2026-09-14):** current head `17127220492339af2d5969003633a7ddbdaf5c45` is based on `main` at `dbf49dad11e30ec5d464be74b715a9a9e31c2c5a`. Rebased across the upstream `deepseek_v4_1` to `deepseek_v41` directory rename and updated the focused test import to the new module path. The original added/removed patch lines are preserved after normalizing that rename; the CUDA source and DSpark caller remain byte-identical. Changed-file pre-commit hooks (`.venv/bin/pre-commit run --files` on all five changed files), `git diff --check`, Python parsing, and a static check of the renamed import target passed. CUDA compilation and GPU/model tests were not rerun for this rebase. GPU/model results below retain the revisions and configurations documented for those earlier runs. AI assistance was used for the rebase, import fix, and validation.

**Related work was found:** #55654 adds uint8 KV-only insertion, fused `kv_norm` and projection changes for V4. There is overlap in the uint8 insertion goal. This PR differs materially by reusing the existing zero-query-head kernel paths across all three cache formats, including BF16/ordinary FP8 paths that #55654 retains as dummy-query fallbacks, and by changing only V4.1 insertion. It does not add another fused norm or projection implementation. The overlapping uint8 API should be consolidated if both approaches proceed. #54674's stacked projections are also a separate operation.

Resubmission of #56320 after `dsv41-feat` merged into `main` in #56214. The original feature-branch PR is closed; this is its existing `main` replacement.

**zyongye** (2026-09-15T20:32:47Z):

Pushed one commit to this branch as a maintainer edit — `8693c714d3`. The KV-only design is unchanged and `test_dspark_context_kv_matches_query_insert` passes 32/32 as written; two fixes on top.

### 1. Zero query heads should keep the warp-per-slot grid

`launchFusedDeepseekV4Templated<..., 0, ...>` fell through to the reduced-grid kernel above `NUM_TOKEN_CUTOFF`. That grid earns its keep by iterating a token's Q heads inside one CTA — with zero Q slots there is nothing to iterate, so it launches one block per token and `if (warpId < slot_end)` leaves seven of every eight warps with no work.

Launch overhead hides this up to roughly 16k tokens in a single insert, which is why the microbenchmarks in the description don't show it. Past that it costs about 2x. One GB300, packed uint8 record, eager, microseconds:

| tokens | 2048 | 16384 | 32768 | 65536 | 262144 |
| --- | ---: | ---: | ---: | ---: | ---: |
| before | 11.45 | 18.53 | 34.94 | 69.61 | 269.92 |
| after | 10.93 | 10.90 | 14.05 | 33.74 | 122.27 |

The "after" row matches a build that always takes the warp-per-slot grid to within noise (33.48 and 122.28 at the last two sizes), so grid shape was the entire difference.

### 2. Record width off the cache tensor rather than `attn.kv_bytes_per_token`

The bound cache already is `[num_blocks, block_size, bytes_per_token]`, so its last dimension *is* the record width — which also makes the reshape a no-op, so that goes too.

The reason to prefer the tensor is that the attribute name is not stable: it has to become `swa_bytes_per_token` once a layer's sliding-window and compressed records can differ in width, which is exactly what an NVFP4 compressed record needs. At that point this caller breaks at runtime while the test still passes, because the `SimpleNamespace` stub supplies the attribute itself. I narrowed the stub to only what `_insert_context_kv` now reads, so it can't paper over that again.

`block_size` deliberately stays the layer's rather than `cache.shape[1]`: `shape[1]` is *states* per page while the kernel's slot math wants *tokens*, and the two coincide only because the sliding-window cache stores one state per token. Keeping the layer's value also leaves the op's own `size(1)` check cross-checking the two instead of restating the tensor.
