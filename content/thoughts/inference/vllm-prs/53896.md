## Purpose

support https://huggingface.co/Qwen/Qwen3.8-Flash-Next

## How to run

```
vllm serve Qwen/Qwen3.8-Flash-Next
          --served-model-name qwen3.8-flash-next
          -tp 4
          --enable-prefix-caching
          --speculative-config '{"method": "mtp", "num_speculative_tokens": 3}'
```

Enable PLE offload(note PLE offload support is in https://github.com/vllm-project/vllm/pull/53899)

```
VLLM_PLE_CPU_OFFLOAD=1
```

## Validation

- Without offload:
  - Weight formats: BF16, FP8, and NVFP4
  - Platforms: GB300, GB200, H200, and MI355X (BF16 only)
  - Parallel configurations: TP2, TP4, TEP4

- With N-gram embedding offload:
  - Weight formats: BF16 and FP8 (NVFP4 is not currently supported)
  - Platform: GB200
  - Parallel configurations: TP2, TP4, and DEP4

The validation results were provided by Inferact. See the [vLLM recipe](https://recipes.vllm.ai/Qwen/Qwen3.8-Flash-Next) for details.

**Gap: hybrid-quant checkpoints never activate the FP8 PLE path.**

`_get_ple_embedding_quant_method()` in `vllm/models/qwen4_exp/nvidia/ple_layer.py` gates on `isinstance(quant_config, Fp8Config)`. Workaround that works: unconditionally return `Qwen4ExpPLEFp8EmbeddingMethod()` for the PLE (I used an env-var gate for testing). A cleaner fix might detect FP8 PLE shards from the checkpoint itself, or extend the gate to accept ModelOpt-family configs whose checkpoints carry FP8 PLE shards. **zzw09773** (2026-08-27T02:45:58Z):

While bringing this up on gfx942 we hit an out-of-bounds read that traces back to `CircularBufferSpec`
being classified as a normal token-to-slot cache group. Filed the kernel-side guard separately as
https://github.com/vllm-project/vllm/issues/53982; this is the model-side half.

`CircularBufferSpec.max_num_blocks_per_req()` returns `1`, and `QSAMetadataBuilder` computes the
ring's slot mapping itself (`_build_circular_metadata` → `circular_qsa_slot_mapping`, which uses
only `block_table[req, 0]`). But `gpu_model_runner.py:7387-7390` maps `KVCacheSpecKind.MAMBA` to
`SlotMappingMode.NONE` and everything else to `TOKEN_TO_KV_SLOT`, and `CircularBufferSpec` is not a
`MambaSpec` subclass — it falls through `get_kv_cache_spec_kind()` to `UNKNOWN`. So the generic
per-group kernel runs on this group every step, indexing a 128-token-wide row with raw token
positions, and its result is then discarded.

Suggestion: let the spec declare its own mode (e.g. a `slot_mapping_mode` property on `KVCacheSpec`,
default `TOKEN_TO_KV_SLOT`, overridden to `NONE` on `MambaSpec` and on self-managing side caches)
rather than enumerating exceptions in the runner. That also removes one wasted kernel launch per
group per step.

One caveat if you take this: `NONE` makes `get_block_table_width` use `token_alignment=None`, which
narrows the row to 1. That is correct for `circular_qsa_slot_mapping` (column 0 only), but worth
double-checking nothing else depends on the 128-token-aligned width.

**zzw09773** (2026-08-27T02:47:29Z):

Two things, both aimed at the "which configurations work" table @vadiklyutiy asked for.

## 1. The AMD `ple_layer` cannot load the FP8 checkpoint's n-gram table

With `Qwen/Qwen3.8-Flash-Next-FP8`, startup fails because `ngram_embedding.weight_scale` has no
corresponding parameter. In that checkpoint the PLE n-gram table is stored as `F8_E4M3` across 128
shards with a per-tensor scale (0.000199 in our copy); the AMD embedding path only accepts a BF16
table.

The two files are not symmetric on this. In this PR, `nvidia/ple_layer.py` (1170 lines) defines an
FP8 embedding method — `create_fp8_weight_parameter`, `create_fp8_scale_parameter`, a
`QuantizeMethodBase` subclass, and a `_dequantize_embeddings` helper — while `amd/ple_layer.py`
(1059 lines) contains **none** of those symbols.

Two ways to close it — we are running the first and have the second prepared:

- **Dequantize at load** — read the FP8 shards, multiply by the scale, store BF16. Simple, costs
  the memory difference and some load time. This is what we are serving with.
- **Keep it FP8 and dequantize at lookup** — port the NVIDIA method verbatim, i.e. register the
  FP8 weight + scale parameters and dequantize the gathered rows in `_dequantize_embeddings`.
  We have this prepared as a 7-edit patch against a clean `amd/ple_layer.py`; `F.embedding` on an
  `fp8_e4m3` tensor works on ROCm, so nothing else needs to change. Happy to open it as a PR if
  that is the direction you'd prefer.

## 2. gfx942 data point for the compatibility table

You listed GB300/GB200, H200 and MI355X. Here is **gfx942 / MI325X**, which is a different ROCm
target (CDNA3, FP8 is FNUZ, and the published ROCm image's aiter prebuilts are gfx950-oriented):

|             |                                                                                                           |
| ----------- | --------------------------------------------------------------------------------------------------------- |
| Hardware    | 8× MI325X (gfx942), ROCm 7.2.3                                                                            |
| Parallelism | **TP8 with `--enable-expert-parallel`**                                                                   |
| Context     | `--max-model-len 262144`                                                                                  |
| Speculative | MTP, `num_speculative_tokens=3`, acceptance length 3.32                                                   |
| Throughput  | 152 tok/s single stream; 676 tok/s aggregate at 8-way concurrency                                         |
| Correctness | needle-in-haystack to 250k 3/3; zh-TW output, `reasoning_content`, `qwen3_coder` tool parsing all correct |

One constraint worth putting in the table because it is arithmetic, not a bug:
**pure tensor parallelism is not valid for this checkpoint.** `moe_intermediate_size = 640 = 5×128`
and the FP8 `weight_block_size` is `[128, 128]`, so TP2/4/8 give 320/160/80 per rank, none of which
is a multiple of 128. Expert parallelism is required. (The shared expert is in
`modules_to_not_convert`, i.e. BF16, so it is not subject to this.)

Getting there needed three ROCm-side fixes beyond the PLE one — the spec-decode metadata allowlist,
an aiter JIT race, and a slot-mapping out-of-bounds read (#53982; the model-side half of that one
is in a separate comment on this PR). Filed separately so they don't clutter this thread.

**zzw09773** (2026-08-27T07:31:06Z):

On the ROCm path (`models/qwen3_8_flash_next/amd/qsa.py`), `Qwen3_8FlashNextQSAFlashAttentionBackend`
subclasses `FlashAttentionBackend` and does not override `supports_batch_invariance()`, so it
inherits `return True` from `vllm/v1/attention/backends/flash_attn.py`. But the QSA implementation
does not use FlashAttention: `Qwen3_8FlashNextQSAFlashAttentionImpl.forward_qsa` calls the model's
own `qsa_sparse_paged_attention` Triton kernel.

That kernel is not batch-invariant, and the reason is concrete — the split-K reduction depth is a
function of the number of query rows in the batch:

```python
base_programs = (
  q.shape[0] * k_cache.shape[2]
)  # q.shape[0] = query rows in this batch
small_profile_limit = 8 if block_m <= 8 else 4
if base_programs <= small_profile_limit:
  block_n, target_splits, partial_warps = 16, 64, 4
elif base_programs < 32:
  block_n, target_splits, partial_warps = 16, 32, 4
elif base_programs <= 256:
  block_n, target_splits, partial_warps = 64, 8, 2
elif base_programs <= 512:
  block_n, target_splits, partial_warps = 64, 4, 2
else:
  block_n, target_splits, partial_warps = 64, 1, 2
...
num_splits = min(max_useful_splits, target_splits)
```

`num_splits` sets how many partial accumulators `_qsa_merge_splitk_kernel` combines. Crossing any
of those thresholds changes the reduction tree, and therefore changes the floating-point rounding
of the same request's attention output. That is precisely what `VLLM_BATCH_INVARIANT` is supposed
to rule out.

## Why this is currently latent, and why it will not stay that way

On this model the flag cannot be reached today: `vllm/v1/attention/selector.py` raises before the
attention backend is consulted, because the GDN/mamba backend does not declare batch invariance:

```python
if (
  envs.VLLM_BATCH_INVARIANT
  and not mamba_attn_backend.supports_batch_invariance()
):
  raise RuntimeError(
    f'VLLM batch_invariant mode is not supported for {mamba_attn_backend.get_name()}.'
  )
```

So the incorrect claim is masked by an unrelated guard. The moment mamba/GDN gains batch-invariance
support (#48613 tracks exactly that), this model would start up with
`VLLM_BATCH_INVARIANT=1` and **silently** produce batch-dependent results — the failure mode the
flag exists to prevent. A backend-level capability claim that is only true by accident of a
neighbouring guard is worth fixing before it becomes load-bearing.

## Suggestions

1. **One line, immediate:** override `supports_batch_invariance()` to return `False` on
   `Qwen3_8FlashNextQSAFlashAttentionBackend`. `AttentionBackend` already defaults to `False`; the
   `True` is inherited only because the class reuses `FlashAttentionBackend` for its metadata
   builder.
2. **If QSA should support the flag:** make the profile selection independent of `q.shape[0]` when
   `vllm_is_batch_invariant()` is set — pin `(block_n, target_splits, partial_warps)` to one
   profile so `num_splits` no longer depends on batch composition.

Option 1 is the correct default: declaring `False` costs nothing but an error message, while
declaring `True` wrongly costs silent numerical divergence.

On 8x MI325X (gfx942, ROCm 7.2.3, TP8+EP, MTP with `num_speculative_tokens=3`) this PR's PLE
n-gram context is wrong on **every** decode step in the **default** configuration. Across two
requests we could classify 154 decode steps and **none** of them received a correct n-gram
context. The cause is that
`_prepare_ngram_context` reads the CPU-side token mirror at a point where, under async scheduling,
that mirror still holds the optimistic `-1` placeholders that speculative decoding writes before
acceptance is known.

## The code

`vllm/v1/worker/gpu_model_runner.py` (added by this PR; there is no `_prepare_ngram_context` on
`main`):

```python
num_computed = self.input_batch.num_computed_tokens_cpu
token_ids = self.input_batch.token_ids_cpu
for req_idx in range(num_reqs):
  end = int(num_computed[req_idx])
  start = max(0, end - self.ngram_context_len)
  context_tokens = token_ids[req_idx, start:end]
  ...
  context_cpu[req_idx, -context_tokens.size :] = context_tokens
```

`end` is fine — in `mamba_cache_mode == "align"` the deferred speculative correction is forced
before `_preprocess` runs, so `num_computed_tokens_cpu` is already corrected. The problem is the
**contents** of `token_ids_cpu` at `[end - ngram_context_len : end]`.

Under async scheduling with speculative decoding, `CachedRequestState.output_token_ids` is extended
with optimistic placeholders:

```python
optimistic_num_accepted = req_state.prev_num_draft_len
req_state.output_token_ids.extend([-1] * optimistic_num_accepted)
```

and `GPUInputBatch` documents the same thing: _"async spec decode adds optimistic placeholders that
may exceed the actual acceptance count."_ Those placeholders reach `token_ids_cpu` through
`_update_states`, and are only replaced later.

## What we measured

Instrumented `_prepare_ngram_context` to log, per call, the sliced context `ctx`, the surrounding
row `token_ids_cpu[req, end-4:end+2]`, and `output_token_ids[-3:]`. Three requests, 178 calls:

| phase         | `end` | `ctx` (the two ids fed to the n-gram)               | `output_token_ids[-3:]` |
| ------------- | ----- | --------------------------------------------------- | ----------------------- |
| prefill chunk | 24    | `[321, 264]` — real tokens                          | `[]`                    |
| prefill tail  | 36    | `[248069, 271]` — real tokens                       | `[]`                    |
| decode        | 39    | **`[-1, -1]`**                                      | `[-1, -1, -1]`          |
| decode        | 43    | `[198, 248045]` — stale, not this position's tokens | `[-1, -1, -1]`          |
| decode        | 47    | **`[-1, -1]`**                                      | `[-1, -1, -1]`          |
| decode        | 63    | **`[-1, 0]`**                                       | `[-1, -1, -1]`          |

The first decode step is already wrong: `end=39`, `ctx=[-1, -1]`, where the correct context is
`[271, 248069]`. The two requests use the identical prompt and produce _different_ sequences of
wrong values.

Two distinct wrong values appear, and they matter differently:

- **`-1`** is the optimistic placeholder described above — a sentinel that was never meant to reach
  an embedding lookup.
- **`0`** is a **valid token id**, not a sentinel. It comes from positions of `token_ids_cpu` that
  were never written for this request (the buffer is zero-initialised). So those steps do not fail
  or clamp; they silently feed the embedding for token id 0.

## Why this surfaced as nondeterminism

We found it while chasing run-to-run nondeterminism with greedy decoding. A per-layer activation
bisection put the first divergence at **layer 1's PLE output**, with every other layer bit-identical
up to that step. Within the PLE input, only the **first two** of the four query rows differed —
which is exactly the set of rows whose 2-/3-grams reach outside the current step and therefore
consume `ngram_context` (`ngram_size = 3`). Running with `--no-async-scheduling` made 16/16 probe
runs bit-identical, including the first request after boot.

## The same PR already contains the correct pattern, twice

1. `preprocess_mamba` reads CPU-side state too, and this PR's runner explicitly forces the deferred
   correction before it, with a comment saying why:

   ```python
   if self.cache_config.mamba_cache_mode == 'align':
     # preprocess_mamba reads req_state.num_computed_tokens (CPU)
     # to decide copy operations, so we must apply deferred
     # corrections before it runs.
     if deferred_state_corrections_fn:
       deferred_state_corrections_fn()
   ```

   `_prepare_ngram_context` reads CPU-side state as well but has no equivalent guard.

2. The PR also ships a model-runner-V2 implementation whose class docstring is _"Add rollback-safe
   PLE n-gram context to the model inputs."_ — i.e. the author identified this exact hazard. But
   **that path is unreachable for this model**: `Qwen3_8FlashNextForCausalLM` /
   `Qwen3_8FlashNextForConditionalGeneration` are not in
   `DEFAULT_V2_MODEL_RUNNER_ARCHITECTURES`, and the model is hybrid, so
   `_is_default_v2_model_runner_model()` returns `False` and V1 always runs. (Checked against
   `main`: the architecture list there does not contain them either.)

So the safe design exists in the PR, on a path this model cannot take.

## Suggested fixes, cheapest first

1. **Filter placeholders.** Treat `-1` (and any not-yet-written slot) as "no context" and fall back
   to the eos fill the function already uses, rather than feeding it to the embedding.
2. **Take the confirmed tail.** Build the context from the last _confirmed_ entries of
   `req_state.output_token_ids` rather than from the optimistic CPU mirror.
3. **Order it like mamba.** Call the n-gram context preparation after the deferred correction and
   after the sampled-token write-back, the way `preprocess_mamba` is handled today.
4. **Or make the V2 "rollback-safe" path reachable** for these architectures.

(1) alone removes the `-1` case; it does **not** fix the stale-value case, so we would expect (2)
or (3) to be the real fix.

| where                                                         | value  | why                                                    |

## Why we think the invariant is not established

`capacity` is a function of `(compress_ratio, num_speculative_tokens)`. `block_size`, on this
model, is resolved from the hybrid-allocator page-size relationship between the GDN/mamba state and
the attention KV — quantities with no semantic relationship to the ring. The divisibility is
therefore coincidental, and it holds only while `cdiv(span, compress_ratio)` happens to be a power
of two (i.e. `nst ≤ 4` here).

We did not trace where the "LCM" the comment refers to is computed, so we cannot say whether the
ring spec is simply absent from it or whether it runs before `num_speculative_tokens` is known.
That part is inference from the observed numbers, not from reading that code path.

   `AssertionError` and an unhealthy container, with nothing indicating that the fix is to change
   `num_speculative_tokens`.
2. **Round the capacity to a power of two** (`capacity = 1 << (span - 1).bit_length()` or similar).

   block size. The cost is at most 2× the ring, which is one block per request.
3. **Or genuinely include the ring capacity in whatever computes `block_size`**, so the comment's
   claim becomes true.

## SM80 (Ampere) enablement: working e5m2 route, verified on 4× CMP 170HX

Since the sm_80 build issue was raised (thanks @vowstar), sharing a **working Ampere route** that we've deployed and measured on real hardware — hoping it helps shape SM80 support in this PR.

### Approach (no kernel changes, ~20 lines)

SM80 has no `fp8e4nv` in Triton (needs SM89+), but **`fp8_e5m2` compiles fine** (software-emulated → BF16 compute on native tensor cores). We re-routed the model's FP8 pipeline to e5m2 on top of the official `qwen38-flash-next` docker image:

1. `platforms/interface.py` → `fp8_dtype()` returns `float8_e5m2` when `capability == (8, 0)`
2. `quantization/fp8.py` → `create_weights`: hardcoded `e4m3fn` replaced with `current_platform.fp8_dtype()`
3. `quantization/utils/fp8_utils.py` → non-e4m3 dtypes route through the in-function Triton fallback (the prebuilt CUDA `per_token_group_quant_8bit_fp8` op rejects e5m2)
4. `fused_moe/experts/triton_moe.py` → admit `float8_e5m2` in the dtype allowlist + both `compute_type` tables (→ `tl.bfloat16`)

The checkpoint stays official e4m3 on disk; loader-side `copy_()` converts to e5m2 at load time (same 1 byte/weight, block scales preserved). Same spirit as the MiniMax-M3 SM80 work (Hakureirm/minimax-m3-ampere).

### Measured on 4× CMP 170HX 64GB (GA100, PCIe Gen2 x16, no NVLink), TP4

| Metric                     | Result                                            |
| -------------------------- | ------------------------------------------------- |
| max-model-len              | **262,144** (native max)                          |
| piecewise CUDA graphs      | 51/51 captured                                    |
| decode (stream, greedy)    | **37.6–37.9 tok/s** sustained; 52.4 peak @32K ctx |
| TTFT (warm)                | 262 ms; 64K prefill ≈ 56,000 tok/s                |
| tool calls (`qwen3_coder`) | round-trips correctly                             |

1. `--kv-cache-dtype fp8_e5m2` is hard-rejected by QSA (`qsa.py:187` — "requires a BF16 main KV cache"). Fine in practice since the MLA-compressed KV is small, but a friendlier error message might save others some debugging time.
2. MTP (`num_speculative_tokens=3`) measured **net-negative** on SM80: accept rates 65/42/28%, but per-step verification overhead on emulated-FP8 MoE eats the gains (21–22 tok/s vs 37.9 without). Possibly SM80-specific; fine elsewhere.

**One caveat that cost us a while, worth folding into whatever lands.** Under PLE **CPU offload**
the GPU-side process must _not_ register `weight` / `weight_scale`. `load_weights()` retains only
`_offload_weight_scale`; a registered-but-never-loaded `weight_scale` then shadows it in

fails **silently** — no error, correct-magnitude activations, fluent but wrong output. So the gate
needs to stay closed in the GPU process when offload is active:

```python

  return None
```

**Two things from profiling this model on GB10 that may be useful to the thread.**

**1. Single-stream decode is bandwidth-bound on the _unquantized dense_ weights, not on the
experts.** Torch profiler over a steady-state decode, TP=1, no speculation, 58.8 ms/token:

|                               | ms/token | % of wall |

| cutlass GEMM (the NVFP4 path) |    15.80 |     26.9% |
| MoE experts                   |     0.47 |      0.8% |

GPU is 95.5% busy (union of 253,529 kernel intervals across 52 streams), so this is not a
scheduling or graph-break effect. `RadixArk/Qwen3.8-Flash-Next-NVFP4` leaves ~4.84 B **dense**
params in BF16 — attention q/k/v/o, GDN projections, dense mlp, lm_head, shared_expert — read in
full every token: 9.68 GB of a 10.98 GB per-token budget. At 273 GB/s that is a 35.5 ms floor, and
an independent bandwidth model lands within 15% of the profiler. The properly-NVFP4 experts cost
0.47 ms/token by comparison. An "A6B" model moving 11 GB/token is the headline.

[hashd1ve](https://github.com/hashd1ve/qwen38-flash-next-one-dgx-spark) reached the same
conclusion independently and earlier, from SGLang.

## FP8 KV cache for QSA works, and it is a small change

`Qwen4ExpQSAFlashAttentionBackend` currently declares `["auto", "bfloat16"]`, so Flash-Next is limited to a BF16 pool. Almost everything needed is already in place: `do_kv_cache_update` is inherited and already quantizes through `reshape_and_cache_flash` with the layer scales, `set_default_quant_scales` is already called in the layer constructor, and the pool halves by itself once the spec dtype is FP8, since `AttentionSpec` sizes pages from `get_dtype_size`.

What was missing is the read side: `_qsa_sparse_paged_gqa_splitk_kernel` needs to dequantize on load. The per-tensor key scale folds into the existing `softmax_scale_log2` multiply at no cost, and the value scale applies once to the normalized output, which is exact because a constant commutes through both the softmax normalization and the split-k merge. One detail worth flagging even if you implement this differently: the value dot currently does `probabilities.to(values.dtype)`, which under FP8 would quantize the _probabilities_ rather than the values.

One other thing surprised me. `Qwen4ExpQSAFlashAttentionBackend` inherits `supports_kv_cache_dtype` from `FlashAttentionBackend`, which routes quantized dtypes to `flash_attn_supports_kv_cache_dtype()` and so requires FA3 on SM90 or FA4 on SM100, and refuses `fp8_e5m2` outright; `FlashAttentionImpl.__init__` raises on the same condition. QSA never calls FlashAttention's attention kernels, so on SM120 FP8 gets refused for a reason unrelated to SM120. Only the arch-independent `reshape_and_cache_flash` write path actually reads the cache dtype.

**`lm_head` cannot be quantized on this model, and one of the three reasons is in this PR's own
model file — worth a one-line change before merge.**

`lm_head` is BF16 `[248320, 2560]` in every published GPU checkpoint of Flash-Next (verified across
ten). That is not a checkpoint choice. Three independent things block it, and any one alone is
sufficient:

**1. This PR's model file never passes `quant_config` to `ParallelLMHead`.**

`vllm/models/qwen3_8_flash_next/nvidia/model.py`:

```python
self.lm_head = ParallelLMHead(
  config.vocab_size,
  config.hidden_size,
  prefix=maybe_prefix(prefix, 'lm_head'),  # <- no quant_config
)
```

`VocabParallelEmbedding.__init__` then sees `quant_config is None` and installs
`UnquantizedEmbeddingMethod` unconditionally — `get_quant_method` is never called, so a checkpoint
declaring `lm_head` in `quantized_layers` is silently ignored. `self.quant_config` is already in
scope two lines up, and `ParallelLMHead` already accepts the kwarg:

```python
quant_config = (self.quant_config,)
```

Same in `mtp.py`, which constructs its own `ParallelLMHead` the same way.

**2 and 3 are not this PR's** — recording them so the picture is complete. `config.json`'s
`quantization_config.ignore` contains `lm_head` in the checkpoints we tested (so `is_layer_excluded`
returns early), and `VocabParallelEmbedding`'s vocab-aware loader asserts
`loaded_weight.shape[output_dim] == self.org_vocab_size`, which is true of `weight` and false of a
block-scale companion shaped `[1940, 20]` — the embedding loader has no notion of a scale tensor.
We worked around the third locally by attaching a plain copy loader to the scale parameters, with
an explicit `NotImplementedError` for TP>1 since the scale would need sharding in _block_ space.

**Why it is worth supporting: measured on one GB10, TP=1.**

|           | `lm_head` BF16 | `lm_head` FP8 blockwise |
| --------- | -------------: | ----------------------: |
| code      |     23.2 tok/s |                **26.1** |
| factual   |     23.7 tok/s |                **26.2** |
| NLL/token |         0.9687 |              **0.9628** |
| tasks     |          10/10 |                   10/10 |

Paired NLL over 14 chunks / 646 tokens of held-out prose, code, German, French and technical text;
9 chunks better and 5 worse, so we read the −0.6% as noise and report it as **no measurable
quality cost**, not as an improvement. **+11% decode** matches a bandwidth model: at `[248320,
2560]` the head is 1.27 GB read on every token, of a ~7.25 GB per-token budget.

Format matters more than the layer: on the sibling Qwen3.8-27B we previously measured an **NVFP4**
head at 2.4% worse NLL and declined it, while an **FP8** head is loss-neutral.

One prefix note for anyone implementing: vLLM asks about **`language_model.lm_head`**, not
`lm_head`, so a config keyed on the bare name still resolves (the candidate list handles it) but is
worth testing explicitly:


**tsw2k** (2026-08-31T10:56:14Z):

Running this stack in a configuration you may not have tried: TP4 across four DGX Sparks (GB10, sm121), on the day-0 image. Repo with the launcher, patches and measurements: https://github.com/tsw2k/Qwen3.8-Flash-Next-Quad-DGX-Sparks

The good news first: multi-node works. `--nnodes 4` with the mp backend rendezvouses fine, and at native 262k the fleet passes a full gate suite (concurrent ~30k prefills, byte-identical greedy decode, NIAH to 128k, vision, tool calls). 4.7M-token KV pool, 31 tok/s single stream, 157 tok/s aggregate at 16 streams.

Four findings that may be useful for this PR:

1. Plain TP4 cannot load the NVFP4 checkpoint. TP sharding cuts the MoE intermediate 640 to 160 per rank and FLASHINFER_CUTLASS raises `NotImplementedError: Intermediate size padding for w1 and w3`. `--enable-expert-parallel` avoids it. A clearer error message, or implying EP for this case, would save people a boot.

2. `_get_ple_embedding_quant_method` only accepts `Fp8Config`, so `VLLM_PLE_CPU_OFFLOAD=1` with the ModelOpt NVFP4 checkpoint dies loading `ngram_embedding.weight_scale`. The PLE shards are fp8 plus weight_scale either way; accepting `ModelOptNvFp4Config` there fixes it.

3. The PLE offload worker loads the whole table in one process. On a 128 GB GB10 node its load peak reached ~85 GB anon RSS (the fp8 table plus a temporary copy) and drew a global OOM kill at any gpu_memory_utilization we tried. The `nnodes != 1` check in `_validate_ple_offload_config` looks stricter than the architecture requires, since the worker is spawned per WorkerProc and its pidfd handover is node-local, but memory rather than topology is what stops it on this hardware.

4. The open bug: on the 1M YaRN lane, roughly the third request with a prompt over ~100k tokens hangs a worker's GPU stream. The `sample_tokens` RPC times out and the engine dies. `/health` is 200 until then, and short requests never trigger it. We eliminated, one variable per boot on a rebooted fleet: prefix caching, MTP, expandable_segments, page cache (an unconditional flusher through serving), chunk size 8192 down to 1024, CUDA graphs (`--enforce-eager` dies identically), and three different PLE paths (the blazux mmap patch, the resident vocab-sharded table, and CPU offload as far as it would go). py-spy shows every surviving rank parked at the first stream-sync point after the wedge, so the hang is in a kernel enqueued earlier in the forward: GDN, QSA or the EP all-to-all.
