# #59733 [Bugfix][Kimi-K3] Declare max_tp_shards on the DSpark MLA KV cache spec

## Overview

Fixes a Kimi-K3 + DSpark perf regression from #57652: the K3 DSpark draft's `MLAAttentionSpec` does not declare `max_tp_shards`, so its MLA layers stop merging with the target's and the KV cache splits from **4 to 20 groups**. One-line fix: declare `max_tp_shards=1` on the draft spec, matching `MLAAttention`.

## Claims

- Restores Kimi-K3 + DSpark to 4 KV cache groups (20 on current `main`).
- Recovers the regression: **+3.7% total throughput/GPU, −3.3% median TPOT** vs. current nightly on MI355X TP8, matching both the pre-#57652 nightly and a full revert of #57652.
- Restores the pre-#57652 GPU KV pool size (3,192,149 → 3,274,215 tokens).
- Keeps #57652's offloading change; no behavior change for K3's offloading `kv_tp_replicas` (KDA layers already pin the gcd to 1).

## Details

**Root cause.** #57652 added `AttentionSpec.max_tp_shards` and set it to `1` in `MLAAttention.get_kv_cache_spec`. `vllm/models/kimi_k3/nvidia/mla.py` (used for the K3 target on NVIDIA and for the DSpark draft on both vendors) builds its own `MLAAttentionSpec` and leaves it `None`. On ROCm the K3 target uses `MLAAttention` (`1`) while the draft uses this class (`None`), so `MLAAttentionSpec.merge`'s per-field `AttentionSpec` equality check rejects them. `_get_kv_cache_groups_uniform_page_size` then sees buckets of 69 KDA / 24 target MLA / 5 draft MLA layers instead of 69 / 29, the group size drops from 29 to 5, and the group count goes from 4 (3 KDA + 1 MLA) to 20 (14 + 5 + 1). The server log shows `kv cache group sizes` growing from 4 to 20 entries and `Add 1 padding layers` twice instead of `Add 18 padding layers`.

**Why 20 groups is slower.** `_build_attention_metadata` builds per KV cache group each step, and neither the ROCm K3 KDA builder nor the AITER MLA builder supports `update_block_table` reuse, so every extra group is a full `builder.build()` plus its own block-table/slot-mapping work.

**Why `1` is correct.** The draft's MLA latent KV has a single head and is replicated across TP ranks, same as `MLAAttention`. On NVIDIA the target and draft both go from `None` to `1`, so they still merge and grouping does not change. `kv_tp_replicas` remains 1 for K3 because its KDA (Mamba) layers contribute 1 to the gcd, so offloading behavior is unchanged.

**Not duplicate.** No open PR sets `max_tp_shards` on the K3 draft spec. #57942 (draft) adds a separate AMD DSpark MLA module, and #58207 changes the group-size heuristic. Both are broader and neither fixes this mismatch on `main`. This PR is the minimal fix for the regression.

Some notes on scope: why only Kimi-K3 + DSpark on ROCm regresses after #57652, and why other target + MTP/draft pairs don't.

**When #57652 changes grouping.** `MLAAttentionSpec.merge` compares every `AttentionSpec` field, and `max_tp_shards` is now one of them. `_get_kv_cache_groups_uniform_page_size` puts layers in one bucket only if `merge()` succeeds. So grouping changes only when a model has target and draft layers that used to merge and now differ in `max_tp_shards` alone. That happens only when the target and the draft build their specs in different code, and one of those places sets the field while the other doesn't.

**Kimi-K3 + DSpark on ROCm meets that condition.** The ROCm target MLA goes through the generic `MLAAttention` (`max_tp_shards=1`). The registry maps `K3DSparkForCausalLM` to `kimi_k3/nvidia/dspark_mla.py` on both vendors, and that file uses the spec from `kimi_k3/nvidia/mla.py`, which leaves the field `None`. K3's layer counts make the effect large: 69 KDA, 24 target MLA and 5 draft MLA layers. The smallest bucket, now the 5 draft layers, sets the group size, so it falls from 29 to 5 and the group count rises from 4 to 20.

**Pairs that are not affected (checked on `main`):**

| model + draft                               | target MLA spec                                                                       | draft MLA spec                                           | effect                            |
| ------------------------------------------- | ------------------------------------------------------------------------------------- | -------------------------------------------------------- | --------------------------------- |
| Kimi-K3 + DSpark, ROCm                      | `MLAAttention` (1)                                                                    | `kimi_k3/nvidia/mla.py` (`None`)                         | **4 → 20 groups**                 |
| Kimi-K3 + DSpark, NVIDIA                    | `kimi_k3/nvidia/mla.py` (`None`)                                                      | same class (`None`)                                      | equal, still merges               |
| Kimi-K3 + MTP, ROCm / NVIDIA                | platform `KimiDecoderLayer` MLA                                                       | same `KimiDecoderLayer` (`amd/mtp.py`, `nvidia/mtp.py`)  | equal                             |
| DeepSeek V3 / V3.2 + MTP                    | `MLAAttention` (1); V3.2 indexer `DeepseekV32IndexerCache` (1)                        | same classes                                             | equal; #57652 set 1 on both       |
| DeepSeek V4                                 | `deepseek_v4/*` (1)                                                                   | same classes                                             | equal                             |
| DeepSeek V4.1 + DSpark                      | `deepseek_v41/attention.py` `DeepseekV4Attention` / `DeepseekV4IndexerCache` (`None`) | `deepseek_v41/{amd,nvidia}/dspark.py` use the same class | equal (both `None`)               |
| MiniMax-M3 + MTP                            | indexer `minimax_m3/common/indexer.py` (`None`, `cache_role=INDEXER`)                 | MTP has no indexer                                       | nothing to merge with             |
| Qwen4-exp + MTP                             | `QSACompressedKeyCache` (`None`, `tokens_per_state>1`)                                | MTP uses standard attention (`Qwen3_5Model`)             | different spec type, never merged |
| EAGLE3 / Qwen3-DSpark drafts on MLA targets | MLA                                                                                   | standard attention (`FullAttentionSpec`)                 | different spec type, never merged |

So this one-line fix covers every grouping regression from #57652 on `main`.

**Remaining `None` builders.** The builders that still leave the field `None` (`deepseek_v41/attention.py` ×2, `minimax_m3/common/indexer.py`, `qwen4_exp/common/qsa_cache.py`) don't change grouping. However, `kv_cache_groups_tp_replicas` treats `None` as "not replicated", so they keep `kv_tp_replicas` at 1. That only matters for #57652's replicated-layout KV offload path. Could they get `max_tp_shards=1` in a follow-up? For QSA, someone should first confirm the compressed key cache is identical on every TP rank. Also, `merge()` keys grouping on `max_tp_shards`, a field that only describes TP sharding. That makes this kind of split easy to reintroduce whenever a new builder forgets the field. Comparing it outside the grouping key, or defaulting it from `num_kv_heads == 1`, would remove that trap.
