# #49718 [Attention] Add FlashInfer XQA decode support on SM12x

https://github.com/vllm-project/vllm/pull/49718 · askliar · MERGED · created 2026-07-24T12:14:19Z · merged 2026-08-11T23:32:49Z

## Summary

Enable FlashInfer XQA decode on SM120/SM121 through FlashInfer's dedicated XQA API.

- Select XQA for SM12x decode.
- Support uniform and ragged speculative decode through `q_len_per_req` and `q_cu_seq_lens`.
- Build the packed causal or non-causal draft mask required by XQA.
- Support sliding-window decode, attention sinks, non-causal draft attention, and uniform-batch CUDA graphs on SM12x.
- Keep the existing SM90 shared-XQA path and SM100 trtllm-gen path unchanged.
- Align the Python, cubin, JIT-cache, and Docker pins on FlashInfer 0.6.16.post1.

## Dependency

This PR requires [FlashInfer 0.6.16.post1](https://github.com/flashinfer-ai/flashinfer/releases/tag/v0.6.16.post1), which includes the required upstream support from [flashinfer#4137](https://github.com/flashinfer-ai/flashinfer/pull/4137) and [flashinfer#4199](https://github.com/flashinfer-ai/flashinfer/pull/4199). The Python, cubin, and CUDA-specific JIT-cache artifacts are available in the release.

## Scope

This is not a duplicate of #47306 or #37592. Those drafts target the legacy shared decode API and older FlashInfer/base revisions; this PR is limited to SM12x and targets the dedicated 0.6.16.post1 XQA API.

SM90 enhancements and SM100 changes are intentionally excluded and will be handled separately.

SM12x NVFP4 KV-cache support is also out of scope and should build on this PR through #49818.

## SM12x NVFP4 integration note

This PR's SM12x XQA routing and the NVFP4 enablement in #49818 are complementary, but they overlap in `vllm/utils/flashinfer.py` and `vllm/v1/attention/backends/flashinfer.py` and will need an explicit integration order.

The current revision here enables XQA for SM90/SM12x only when `kv_cache_dtype.startswith("fp8")`. Its NVFP4 initialization still requires both TRTLLM prefill and decode support, and the wrapper path still treats NVFP4 as trtllm-gen-only. Therefore this PR does **not** enable SM120 NVFP4 KV.

The accompanying claim that XQA does not support NVFP4 KV needs narrowing. FlashInfer 0.6.15's XQA implementation has an SM120 NVFP4-KV path. #49818 carries the additional vLLM-side pieces required to reach it safely:

- the SM120 NVFP4 dtype/dispatch gate;
- FA2 prefill plus XQA decode;
- model-dtype Q/O and FP8-output-buffer handling;
- the SM120 5-D NVFP4 layout fix for the #44455 regression.

That layout point is load-bearing on RTX 5090: current-main gates without it produced token-id-0 collapse 5/5, while changing only the NVFP4 layout produced 5/5 correct; the resulting branch also passed 8/8 concurrency with a 13,158-token needle. The fuller masked-XQA validation behind #49010 passed 3/3 cold and 3/3 cached ~31k needles under true FULL MTP, with mask rows `1, 3, 7, 15` for q_len=4.

Suggested split: keep this PR as the generic XQA API/mask/cudagraph foundation, then rebase/compose #49818's distinct SM120 NVFP4 contract and layout changes on top. I can run the integrated revision on RTX 5090 once the required FlashInfer 0.6.16 artifacts are available. Related root-cause trail: #49010, #49011, #49818.
