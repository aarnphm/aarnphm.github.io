# #61024 [Roadmap] vLLM Roadmap Q4 2026

https://github.com/vllm-project/vllm/issues/61024 · simon-mo · OPEN · created 2026-10-10T19:21:47Z

In [#32455](https://github.com/vllm-project/vllm/issues/32455), we broke down vLLM's goals into various special interest groups (SIGs). Building on the [Q3 roadmap](https://github.com/vllm-project/vllm/issues/48168), please find below each SIG's Q4 roadmap. You can find regular meetings of these SIGs on the public vLLM calendar.

## Key takeaway

- **Agentic Workload:** Q3 established Model Runner V2 as the default and brought production-ready Rust frontend and distributed KV offloading support. Q4 focuses on making optimized agentic serving easier to deploy: better day-0 performance, tuned production recipes, adaptive speculative decoding, richer agent hints, and fault tolerance across hardware.
- **Ecosystem:** We are expanding low-precision serving and checkpoint conversion across NVIDIA and AMD, strengthening speculative decoding and RL integration, and advancing Agentic API and vLLM-Omni. Frontier models and new hardware need a clear path from initial support to validated, optimized production configurations.
- **OSS Maintenance:** We are simplifying engine and model interfaces, completing quantization dispatch refactors, and improving CI coverage, time to signal, security, and performance evaluation. Agent-assisted review and better test-quality checks should help the community maintain a growing model, feature, and hardware matrix.

- [ ] **Production FP4 and lower-bit KV caches:** publish accuracy evaluations and recommended configurations for priority models. Cover long-context interactive serving and high-concurrency data generation, and compose with hybrid attention, speculative drafters, NIXL disaggregation, and tiered offloading.
  - Expand NVFP4 coverage across FlashMLA/DSA sparse attention, FA4, Rubin kernels, and [SM8x–SM12x enablement](https://github.com/vllm-project/vllm/pull/46963).
  - Advance ROCm low-bit KV work, including [UltraQuant](https://github.com/vllm-project/vllm/pull/57057) and the [Octave KV proposal](https://github.com/vllm-project/vllm/issues/59773), with platform-specific validation rather than assuming one format fits every backend.
- [ ] **Checkpoint requantization:** complete the [online quantization from arbitrary precision roadmap](https://github.com/vllm-project/vllm/issues/59062) through a common online quantization API, including [requantization](https://github.com/vllm-project/vllm/pull/55684), [activation QuantKey overrides](https://github.com/vllm-project/vllm/pull/51808), [shared experts](https://github.com/vllm-project/vllm/pull/55686), and [MLA `kv_b_proj`](https://github.com/vllm-project/vllm/pull/55741). Initial conversions include MXFP8 to FP8 per-channel/block on Hopper and MI300, and FP8/NVFP4 to MXFP4 across vendors.
- [ ] **Unified dispatch and inspectability:** finish QuantKey/QuantConfig adoption in [Quark](https://github.com/vllm-project/vllm/pull/56099), [ModelOpt MoE](https://github.com/vllm-project/vllm/issues/55339), and compressed-tensors. - [ ] **Compression ecosystem:** deliver day-0 NVFP4/MXFP4 checkpoints for priority models, advance [MoNe](https://github.com/vllm-project/vllm/pull/50415) and [REAP expert pruning](https://github.com/vllm-project/llm-compressor/pull/2906), and make `convert_checkpoint` the general format-conversion entry point.
- [ ] **Quality validation:** add quantized-model accuracy CI, tensor-parallel parity checks for online quantization, and quantized weight-reload correctness checks with the RL ecosystem.

* Research directions: LUT-B attention support, FP4 with rotations through QuTLASS, HIGGS, and QAD. Continue evaluating [legacy format deprecation](https://github.com/vllm-project/vllm/issues/30136).

**ammarali32** (2026-10-26T05:44:04Z):

Hello @simon-mo
we would like to present
Lossless state-tree representation for weights and KV cache (~12 bits per value, bit-exact BF16)

### Motivation.

LLM decoding is memory-bound: every new token re-reads all the weights and the whole KV cache. Today the way to read fewer bytes in vLLM is quantization, which changes the model's numerics.

We have been working on **state trees** https://arxiv.org/abs/2610.31931, a representation in which every value is a path of shared discrete decisions. Its simplest instance shares one exponent node per 64 BF16 values: every weight and every cached key/value is stored in about 12 bits and decodes to its **exact BF16 bits**, with no calibration and no accuracy trade-off.

We implemented it as an out-of-tree vLLM plugin with fused CUDA kernels https://github.com/ammarali32/StateTree-Representation:

- **Weights:** a `LinearMethodBase` for all linear layers, with fused decode-and-multiply kernels for decode and medium batches, and decode + cuBLAS for large prefill.
- **KV cache:** a custom attention backend that stores each 16-token block as a state-tree page, with a decode-attention kernel that reads the compressed pages directly.

Qwen3-8B, one A100-40GB, vLLM 0.32, `gpu_memory_utilization` 0.85:

|                                            | BF16        | statetree           |
| ------------------------------------------ | ----------- | ------------------- |
| Weights in GPU memory                      | 15.3 GiB    | 12.8 GiB            |
| KV-cache capacity                          | 119K tokens | 178K tokens (1.49×) |
| Decode, batch 1                            | 75.6 tok/s  | 97.2 tok/s (1.29×)  |
| Time to the complete answer                | 1.00×       | 1.10–1.28× faster   |
| Decode attention vs paged FlashAttention-2 | 1.00×       | 1.21–2.46× faster   |

Weights and KV values are bit-identical to BF16; outputs match up to floating-point summation order, the same kind of difference as switching GEMM kernels. Prefix caching, chunked prefill, CUDA graphs and tensor/pipeline parallelism all work, and it composes with existing quantization methods (layers they claim stay quantized).

Known limitations: prefill of the weight GEMM runs at 0.87–1.03× of cuBLAS (time to first token 3–15% longer), and the KV backend currently requires BF16 and head size 128.

### Proposed Change.

We would like to upstream this and would value your guidance on the preferred shape:

1. **Weights:** a new method under `vllm/model_executor/layers/quantization` (reuses the existing plumbing), or a separate lossless "representation" option, since it does not change the model's numerics.
2. **KV cache:** a new attention backend selected by a flag (for example `--kv-cache-dtype statetree`), or kept as a plugin backend.
3. **Kernels:** CUDA sources built with vLLM, or loaded from the `statetree` package.

### Feedback Period.

Open. Happy to follow your process.

If you think this will be within your interest, we would be glad to open a PR, add tests (bit-exact round trips, generation equality against BF16) and benchmarks, and maintain the kernels. Would you consider this feature?

**huzaifaasim017** (2026-10-27T12:34:46Z):

For the proposed state-tree KV backend, I would add a cache-lifecycle test before choosing the upstream interface. The reported bit-exact round trip is useful, but a 16-token compressed page is also written incrementally during decode. A request can fork through prefix sharing, append to a partially filled block, then roll back speculative tokens or be cancelled. Those transitions need to preserve the exact pre-fork KV values and avoid exposing a partially re-encoded page to another sequence.

A small deterministic test could compare the plugin backend with BF16 after each append/fork/rollback (including a block boundary and copy-on-write), then run the same trace with prefix caching and chunked prefill enabled. I would also report bytes allocated and decode latency for partially filled blocks, since the 1.49x capacity number for steady state may change when many short agent requests leave tail blocks half full. That evidence would help decide whether the new representation belongs behind a KV cache dtype or a more explicit backend capability.
